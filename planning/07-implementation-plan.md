# 모둠톡 사용자 가치 구현 계획

## 비실행형 경계

이 문서는 17:30 이후 어떤 사용자 가치를 어떤 순서로 증명할지 정한다. 구체적인 구현 작업·명령·프로젝트 구조·코드 생성 프롬프트는 포함하지 않는다.

제품 범위는 [01-product-spec.md](01-product-spec.md), 관찰 가능한 합격선은 [08-acceptance-tests.md](08-acceptance-tests.md)가 기준이다.

## 구현 목표

첫 목표는 모든 기능을 만드는 것이 아니다. 교사가 여러 모둠 중 지금 먼저 살펴볼 곳을 찾고, 모둠 공용 기기가 대화 수집 상태를 이해하는 핵심 시연 6단계를 끝까지 증명하는 것이다.

구현은 각 증분이 사용자에게 보이는 결과를 남기는 순서로 진행한다. 다음 증분은 이전 증분의 관찰 결과가 확인된 뒤 시작한다.

## 우선순위

1. 활동과 역할을 이해하는 최소 흐름
2. 모둠 준비와 교사 시작의 상태 일치
3. 한 모둠의 대화 상태가 교사에게 보이는 관통 흐름
4. 여러 모둠 비교와 먼저 살펴볼 후보
5. 정보 부족·판단 불가·연결 실패·종료
6. 개인정보·분석 한계와 시연 안정화
7. 시간이 남을 때만 보조 분석·사후 보고

## 가치 증분

### 증분 0. 17:30 시작 상태 확인

**사용자 가치**

팀이 제품 문제·핵심 시연·안전 경계를 같은 말로 이해한다.

**결정할 것**

- 새 출품 저장소가 실제 개발 산출물 없이 시작됐는가
- 이번 시연이 합성 데이터 또는 동의한 성인 데이터만 쓰는가
- 핵심 시연 6단계와 비목표에 팀이 동의하는가
- 대상 학교급 미결정이 핵심 시연을 막지 않는가

**관찰 결과**

팀원이 “교사는 어느 모둠을 먼저 볼지 찾고, 모둠은 수집 상태를 안다”는 목표와 보조 기능 제외를 설명할 수 있다.

**중단 기준**

기존 참고 구현의 구체 구조를 복사해야 다음 결정을 내릴 수 있다면 멈추고 의미 수준으로 다시 올린다.

### 증분 1. 역할과 활동 흐름

**사용자 가치**

교사와 모둠 공용 기기가 서로 다른 역할과 같은 활동 맥락을 이해한다.

**포함 결과**

- 교사는 활동·주제·모둠을 본다.
- 모둠 공용 기기는 활동·주제·선택 모둠을 확인한다.
- 잘못 선택한 모둠을 다시 선택할 수 있다.

**관찰 조건**

[08-acceptance-tests.md](08-acceptance-tests.md)의 1–4, 19번을 확인한다.

**중단 기준**

교사와 모둠 역할이 한 화면이나 같은 상태로 뒤섞여 사용자가 자신이 해야 할 일을 설명하지 못한다.

### 증분 2. 준비와 활동 시작

**사용자 가치**

교사는 어느 모둠이 준비됐는지 보고 활동을 시작하며, 모둠 공용 기기는 대기에서 진행 상태로 바뀐다.

**포함 결과**

- 준비 전·준비됨·확인 필요를 구분한다.
- 교사의 시작 결정과 모둠의 수집 준비 상태가 일치한다.
- 늦은 입장을 참여 부족으로 보지 않는다.

**관찰 조건**

인수 조건 2, 4–6, 20번을 확인한다.

**중단 기준**

교사와 모둠이 활동 시작 여부를 다르게 이해하거나 공용 기기 상태가 개인 학생 출석처럼 보인다.

### 증분 3. 한 모둠의 대화 상태 관통

**사용자 가치**

한 모둠의 대화 수집 상태와 참여 경향이 교사에게 보이고, 모둠은 수집 목적과 현재 상태를 이해한다.

**포함 결과**

- 모둠 공용 기기는 수집 중과 연결 종료 행동을 본다.
- 교사는 정보 부족에서 참여 경향으로 바뀌는 흐름을 본다.
- 익명 화자 표시와 학생 이름을 구분한다.
- 참여 정보는 학생 평가가 아니라고 표시한다.

**관찰 조건**

인수 조건 7–11, 25–27번을 확인한다.

**중단 기준**

교사가 내부 상태만 보고 사용자 의미를 설명하지 못하거나, 참여 경향이 학생 평가처럼 보인다.

### 증분 4. 여러 모둠 비교와 우선 확인

**사용자 가치**

교사가 여러 모둠 가운데 먼저 살펴볼 후보와 이유를 찾는다.

**합성 사례**

- 햇살: 여러 익명 화자가 고르게 참여하는 경향
- 나무: 한 익명 화자 중심 경향
- 바다: 정보 부족
- 구름: 연결 실패

**포함 결과**

- 네 상태를 한눈에 구분한다.
- 교사는 나무를 먼저 살펴보고 구름에는 연결 확인이 먼저임을 안다.
- 정보 최신성과 판단 한계가 함께 보인다.

**관찰 조건**

인수 조건 12–15번을 확인한다.

**중단 기준**

상태가 많아 핵심 판단을 가리거나, 정보 부족·연결 실패가 참여 문제처럼 보인다.

### 증분 5. 실패 회복과 종료

**사용자 가치**

사용자가 연결 문제에서 회복하고 활동 종료 후 수집이 끝났음을 안다.

**포함 결과**

- 연결 실패와 다시 연결 행동
- 회복 후 새 정보 충분성과 최신성 확인
- 활동 종료와 늦게 도착한 정보의 구분
- 실시간 수집 종료와 정보 보존 미결정의 구분

**관찰 조건**

인수 조건 13–18, 21–24번을 확인한다.

**중단 기준**

연결 실패가 참여 문제로 보이거나 종료된 활동이 다시 진행 중으로 보인다.

### 증분 6. 시연 안전성과 패키지 한계

**사용자 가치**

심사자와 실제 도입 검토자가 핵심 가치와 제품 한계, 데이터 안전 경계를 구분한다.

**포함 결과**

- 합성 또는 동의한 성인 데이터 표시
- 수집 목적·열람 주체·종료 상태 안내
- 학생 평가 제외와 익명 화자 한계
- 학교급·보존·삭제·실제 도입 절차의 미결정 표시

**관찰 조건**

인수 조건 25–30번과 시연 합격선 네 항목을 확인한다.

**중단 기준**

실제 학생 정보가 필요하거나 미결정이 법률·정책 보증처럼 보인다.

### 증분 7. 선택적 확장

**시작 조건**

증분 1–6과 핵심 시연 합격선이 모두 통과하고 시연 안정화 시간이 남는다.

**선택 가능한 가치**

- 대화 단계
- 주제 관련성·근거
- 요약·키워드
- 사후 보고

**관찰 조건**

인수 조건 31–34번을 확인한다.

**중단 기준**

확장 기능이 핵심 시연의 안정성·명확성·개인정보 안내를 해치면 즉시 중단한다.

## 일정 지도

시간은 사용자 가치 증분의 우선순위를 조정하는 기준이며 구체 구현 지시가 아니다.

| 시간대 | 목표 | 반드시 남길 관찰 결과 |
|---|---|---|
| 17:30–19:00 | 증분 0–2 | 역할·활동·모둠 확인·준비·시작을 처음부터 걸을 수 있음 |
| 19:00–21:00 | 증분 3 | 한 모둠의 수집 상태와 참여 경향이 교사에게 보임 |
| 21:00–23:00 | 증분 4–5 | 여러 모둠 비교, 오류 구분, 종료가 동작함 |
| 23:00–24:00 | 증분 6과 핵심 시연 반복 | 합성 시연을 처음부터 끝까지 안정적으로 반복함 |
| 24:00 이후 선택 | 증분 7 또는 안정화 | 핵심 합격선을 해치지 않는 범위만 추가함 |

진행 속도가 늦으면 확장 기능을 줄이고 증분 1–6을 우선한다.

## 의존성

```text
역할·활동 흐름
  → 준비·활동 시작
  → 한 모둠의 대화 상태 관통
  → 여러 모둠 비교
  → 실패 회복·종료
  → 시연 안전성·한계
  → 선택적 확장
```

각 증분은 앞 증분의 사용자 상태와 의미를 소비한다. 확장 기능은 핵심 시연과 분리되어 실패해도 증분 1–6을 망가뜨리지 않아야 한다.

## 핵심 위험과 대응

| 위험 | 조기 신호 | 대응 | 포기할 것 |
|---|---|---|---|
| 음성·연결이 시연에서 불안정함 | 정보가 늦거나 갱신이 멈춤 | 합성 상태를 통해 사용자 흐름과 오류 구분을 먼저 검증 | 실시간 정확성 과시 |
| 참여 경향이 학생 평가처럼 보임 | 점수·순위·개인 이름 중심 표현 | 모둠 수준 경향, 익명 화자 한계, 평가 제외를 앞에 표시 | 개인 평가 기능 |
| 정보 부족과 연결 실패가 섞임 | 모든 문제가 같은 경고로 보임 | 데이터 상태와 기술 상태를 분리하고 다음 행동을 다르게 제시 | 단일 만능 상태 |
| 문서·화면이 보조 기능으로 팽창 | 핵심 시연 전에 요약·관련성 작업을 시작 | 확장 증분을 마지막으로 미루고 핵심 합격선 재확인 | 보조 분석 완전성 |
| 실제 학생 데이터가 필요해짐 | 시연 자료에 학생 이름·음성이 등장 | 합성 또는 동의한 성인 데이터로 교체 | 실제 학생 사례 |
| 새 저장소에서 구조 결정을 오래 논의함 | 사용자 결과보다 내부 구조 토론이 길어짐 | 다음 인수 조건을 통과시키는 가장 작은 사용자 가치로 돌아감 | 과도한 미래 확장 설계 |

## 데모 생명줄

실시간 대화 흐름이 불안정해도 제품의 사용자 가치를 검증할 수 있도록 네 합성 모둠 상태를 준비한다.

- 햇살: 정상 참여 경향
- 나무: 먼저 살펴볼 편중 경향
- 바다: 정보 부족
- 구름: 연결 실패

이 생명줄은 실제 동작을 성공했다고 가장하기 위한 것이 아니다. 시연 중 무엇이 실시간이고 무엇이 합성 상태인지 분명히 표시한다.

## 매 증분의 완료 질문

각 증분을 마칠 때 다음을 확인한다.

1. 사용자가 새로 이해하거나 할 수 있게 된 것은 무엇인가?
2. 어떤 자연어 인수 조건이 통과했는가?
3. 핵심 시연 6단계 중 어디가 처음부터 끝까지 이어지는가?
4. 정보 부족·판단 불가·연결 실패·종료가 정상 상태와 구분되는가?
5. 학생 평가·실제 학생 데이터·미결정에 관한 안전 경계를 지켰는가?
6. 다음 증분이 현재 결과에 실제로 의존하는가?

## 최종 구현 완료 조건

- 핵심 시연 6단계를 교사와 모둠 관점에서 반복할 수 있다.
- 네 합성 모둠을 통해 정상·편중·정보 부족·연결 실패를 구분한다.
- 교사가 먼저 살펴볼 모둠과 이유를 설명한다.
- 모둠 공용 기기가 준비·수집·실패·종료와 다음 행동을 이해한다.
- 참여 정보가 학생 평가가 아니며 익명 화자 한계가 보인다.
- 합성 또는 동의한 성인 데이터만 사용한다.
- 보조 기능이 없어도 핵심 시연 합격선을 통과한다.

## 미결정

- 팀 역할 분담과 실제 구현 구조
- 기술·배포·저장·전송 선택
- 대상 학교급과 실제 학생 검증 절차
- 정보 종류별 보존·삭제 책임
- 해커톤의 공식 심사 기준과 상세 허용 수준

이 미결정은 17:30 이후 팀 결정 또는 실제 학생 검증 전에 닫는다.
