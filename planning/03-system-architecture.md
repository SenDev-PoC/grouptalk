# 모둠톡 시스템 아키텍처

## 이 문서의 역할

이 문서는 모둠톡의 시스템 안팎과 주요 논리적 책임, 정보·신뢰 경계, 핵심 시연의 의미 흐름을 설명한다. 제품의 목표와 규칙은 [01-product-spec.md](01-product-spec.md), 사용자 상태와 순서는 [02-user-flow.md](02-user-flow.md)가 기준이다.

이 문서는 비실행형 개념 아키텍처다. 기술·배포·저장·전송·소스 구조는 17:30 이후 새 저장소에서 결정한다.

## 아키텍처 목적

모둠톡의 아키텍처는 다음 제품 결과를 가능하게 해야 한다.

- 교사와 모둠 공용 기기가 같은 활동 상태를 이해한다.
- 여러 모둠의 대화 상태를 교사가 비교할 수 있다.
- 참여 경향, 정보 부족, 판단 불가, 연결 실패를 구분한다.
- 참여 정보가 학생 평가나 확정 진단으로 오해되지 않는다.
- 정보 종류별 목적·열람·보존·삭제의 경계가 드러난다.

## 시스템 경계

### 시스템 밖의 주체

| 주체 | 시스템에 주는 것 | 시스템에서 받는 것 |
|---|---|---|
| 교사 | 활동 준비·시작·종료 결정, 먼저 살펴볼 모둠 선택 | 모둠 준비 상태, 참여 경향, 정보 최신성, 연결 상태, 분석 한계 |
| 학생과 모둠 | 토의 대화, 공용 기기의 모둠 확인·연결 행동 | 수집 목적, 준비·수집·실패·종료 상태 |
| 학교·개인정보 책임자 | 실제 도입 전 목적·보존·권리·외부 처리 기준 | 정보 종류와 수명, 미결정, 제품 한계 |
| 시연 관찰자 | 합성 사례에 대한 관찰과 피드백 | 핵심 문제·사용자 흐름·제품 한계가 드러난 시연 |

### 시스템 안의 논리적 책임

1. 활동 운영
2. 모둠 준비
3. 대화 수집 상태
4. 참여 상태 해석
5. 교사 상황 인식
6. 정보 수명과 투명성

이 책임은 구현 단위가 아니다. 어떤 기술과 구조로 묶거나 나눌지는 17:30 이후 결정한다.

## 논리적 책임 지도

```text
교사
 ├─ 활동 준비·시작·종료 ─────────────▶ 활동 운영
 ├─ 모둠 준비 확인 ◀───────────────── 모둠 준비
 └─ 먼저 살펴볼 모둠 확인 ◀────────── 교사 상황 인식
                                            ▲
                                            │ 참여 경향·최신성·한계
모둠 공용 기기                              │
 ├─ 활동·모둠 확인 ───────────────────▶ 모둠 준비
 ├─ 대화 수집 상태 ───────────────────▶ 대화 수집 상태
 └─ 준비·수집·실패·종료 확인 ◀──────── 활동 운영 / 대화 수집 상태
                                            │
                                            ▼
                                      참여 상태 해석
                                            │
                            정보 종류·목적·수명·한계
                                            ▼
                                      정보 수명과 투명성
```

화살표는 의미 있는 정보와 상태의 이동을 보여 줄 뿐 실제 전송 형식을 뜻하지 않는다.

## 책임별 역할

### 활동 운영

**목적**

교사가 하나의 활동을 준비·시작·종료하고, 교사와 모둠 공용 기기가 같은 활동 상태를 이해하게 한다.

**핵심 책임**

- 활동의 목적과 주제, 참여할 모둠을 사용자에게 보여 준다.
- 시작 전, 진행 중, 종료 상태를 구분한다.
- 교사의 시작과 종료 결정을 모든 사용자 상태에 일관되게 반영한다.

**경계**

- 대화의 내용을 해석하지 않는다.
- 개인 학생의 출석·능력·성취를 판단하지 않는다.

### 모둠 준비

**목적**

모둠 공용 기기가 올바른 활동과 모둠을 확인했고 준비됐음을 교사와 모둠에 알린다.

**핵심 책임**

- 선택한 활동과 모둠을 확인하게 한다.
- 잘못 선택했을 때 시작 전에 바로잡게 한다.
- 준비 전·준비됨·확인 필요·늦은 입장을 구분한다.

**경계**

- 공용 기기의 준비 상태를 개인 학생 출석으로 바꾸지 않는다.
- 모둠원의 실제 신원을 자동으로 판정하지 않는다.

### 대화 수집 상태

**목적**

모둠 공용 기기의 대화 상태가 대기·수집 중·정보 부족·연결 실패·종료 중 어디에 있는지 사용자에게 알린다.

**핵심 책임**

- 수집 시작과 종료를 모둠에 분명히 알린다.
- 정보가 들어오고 있는지, 갱신이 멈췄는지 교사에게 알린다.
- 연결 실패와 다시 연결 행동을 제공한다.

**경계**

- 수집 중이라는 상태가 원본 음성의 장기 보존을 뜻하지 않는다.
- 참여 문제와 연결 문제를 같은 상태로 합치지 않는다.

### 참여 상태 해석

**목적**

교사가 여러 모둠 가운데 먼저 살펴볼 후보를 찾도록 익명 화자의 참여 경향과 판단 한계를 구분한다.

**핵심 책임**

- 고른 참여 경향, 한 화자 중심 경향, 정보 부족, 판단 불가를 구분한다.
- 정보의 양과 최신성이 충분하지 않을 때 결론을 유보한다.
- 익명 화자 표시와 학생 이름을 동일시하지 않는다.

**경계**

- 참여 상태를 학생 평가 점수로 만들지 않는다.
- 자동 해석을 확정 사실이나 교사의 최종 판단으로 제시하지 않는다.
- 내부 판단 방식과 수치는 이 기획에서 정하지 않는다.

### 교사 상황 인식

**목적**

교사가 제한된 주의 안에서 여러 모둠의 상태와 우선 확인 후보를 한눈에 이해하게 한다.

**핵심 책임**

- 모둠별 참여 경향·정보 최신성·연결 상태를 함께 보여 준다.
- 정상 흐름보다 추가 확인이 필요한 모둠과 이유를 먼저 찾게 한다.
- 참여 문제와 기술 문제에 서로 다른 다음 행동을 제시한다.

**경계**

- 교사를 대신해 자동으로 모둠에 개입하지 않는다.
- 많은 정보로 핵심 판단을 가리지 않는다.

### 정보 수명과 투명성

**목적**

원본 음성, 전사문, 익명 화자 표시, 참여 지표, 요약의 목적·열람·보존·삭제·한계를 구분해 숨은 정보 처리를 줄인다.

**핵심 책임**

- 학생과 교사에게 대화 정보의 사용 목적과 보는 주체를 알린다.
- 정보 종류별로 확정 원칙과 미결정을 구분한다.
- 활동 종료와 정보 수명 종료가 같은지 다른지 명시한다.

**경계**

- 이름이 없다는 이유만으로 정보가 익명이라고 보증하지 않는다.
- 해커톤 문서만으로 실제 학교 도입의 법률·정책 적합성을 보증하지 않는다.

## 핵심 시연의 동적 흐름

| 단계 | 중심 책임 | 협력 책임 | 사용자에게 보이는 결과 |
|---|---|---|---|
| 1. 활동 준비 | 활동 운영 | 모둠 준비 | 교사가 활동과 모둠, 준비 상태를 본다. |
| 2. 모둠 확인 | 모둠 준비 | 활동 운영 | 공용 기기가 활동·모둠을 확인하고 교사는 준비됨을 본다. |
| 3. 활동 시작 | 활동 운영 | 대화 수집 상태 | 교사와 모둠이 대기에서 진행 상태로 함께 바뀐다. |
| 4. 대화 수집 | 대화 수집 상태 | 참여 상태 해석, 정보 수명과 투명성 | 모둠은 수집 상태를, 교사는 정보 유무와 최신성을 본다. |
| 5. 먼저 살펴볼 모둠 찾기 | 교사 상황 인식 | 참여 상태 해석, 대화 수집 상태 | 교사는 편중 경향과 연결 실패를 구분해 다음 행동을 고른다. |
| 6. 활동 종료 | 활동 운영 | 대화 수집 상태, 정보 수명과 투명성 | 양쪽이 수집 종료와 남는 정보의 범위를 이해한다. |

## 정보 경계

### 사용자 입력과 관찰 정보

- 교사가 정하는 활동·주제·모둠 정보
- 공용 기기가 확인하는 활동·모둠·준비 상태
- 활동 중 들어오는 대화 정보
- 연결·최신성·종료 상태

### 파생 정보

- 익명 화자 표시
- 참여 경향과 판단 불가 상태
- 확장 범위의 대화 단계·주제 관련성·요약·키워드

파생 정보는 원본보다 정확하거나 확정적이라고 가정하지 않는다. 교사가 볼 때 출처·최신성·한계를 함께 이해할 수 있어야 한다.

## 신뢰 경계

| 경계 | 위험 | 아키텍처 원칙 |
|---|---|---|
| 학생·모둠과 시스템 | 수집 사실과 목적을 모를 수 있음 | 수집 시작·종료와 목적을 공용 기기에 분명히 알린다. |
| 교사와 자동 해석 | 참여 경향을 확정 사실로 오해할 수 있음 | 정보 부족·판단 불가·최신성과 평가 제외를 함께 표시한다. |
| 시스템과 외부 처리 범위 | 대화 정보가 어디서 처리되는지 보이지 않을 수 있음 | 실제 선택 후 처리 주체·목적·보존·삭제를 공개한다. |
| 해커톤 시연과 실제 학교 도입 | 합성 시연을 실제 학생 운영 가능성으로 확대 해석할 수 있음 | 실제 학생 검증 전 학교급·고지·권리·보존 기준을 다시 결정한다. |

## 품질 동인

### 이해 가능성

교사와 모둠은 한 번의 시선으로 현재 상태와 다음 행동을 이해해야 한다. 내부 용어보다 사용자용 상태를 우선한다.

### 최신성과 불확실성

실시간에 가까운 상태가 늦거나 끊길 수 있음을 전제로 한다. 최근 정보, 갱신 중, 갱신 중단을 구분한다.

### 오류 회복

연결 실패가 참여 문제로 보이지 않아야 하며, 모둠 공용 기기는 다시 연결할 행동을 알아야 한다.

### 개인정보와 투명성

정보 종류별 목적·열람·보존·삭제가 구분되어야 하며, 미결정은 숨기지 않는다.

### 제한된 구현 시간

핵심 시연 6단계를 먼저 완성하고 보조 기능은 뒤로 미룬다. 논리적 책임은 이 우선순위를 설명하지만 구체 구현 구조를 강제하지 않는다.

## 핵심과 확장 경계

핵심 아키텍처는 활동 운영, 모둠 준비, 대화 수집 상태, 참여 상태 해석, 교사 상황 인식, 정보 수명과 투명성이다.

대화 단계·주제 관련성·근거·요약·키워드·사후 보고는 핵심 책임과 연결될 수 있지만 필수 시연 경로에 들어오지 않는다. 확장 기능이 실패해도 핵심 시연의 참여 상태와 오류 구분이 동작하면 핵심 가치 검증은 계속할 수 있다.

## 미결정

- 실제 기술·배포·저장·전송 방식
- 참여 경향을 해석할 구체 방법과 검증 기준
- 정보 종류별 실제 보존 기간과 삭제 책임자
- 대상 학교급과 실제 학생 대상 고지·동의 절차
- 외부 처리 주체의 계약과 학교 책임 분담

이 항목은 17:30 이후 구현 또는 실제 학생 검증 전에 결정한다.
